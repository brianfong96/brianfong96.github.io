How passkeys work

The user experience, frontend-to-backend flow, and how passkeys compare with authenticator apps.

First: what a passkey actually is

A passkey is a passwordless FIDO credential—a discoverable WebAuthn credential—scoped to one relying party such as example.com.

Your authenticator Private key Signs locally · never sent to the website
paired
example.com Public key Verifies signatures · safe to store publicly
Protocol familyFIDO2

WebAuthn between the site and browser, plus CTAP when the browser talks to an external authenticator.

WebsiteRelying party

The service that issues challenges, verifies responses, and stores the credential record.

Key holderAuthenticator

A phone, computer, password manager, or security key that creates and uses the credential.

CredentialKey pair + metadata

A private key, public key, credential ID, RP ID binding, user handle, and state flags.

The private key proves

The authenticator uses the private key to sign fresh flow data. The website never needs the private key and never receives it during registration or sign-in.

The public key verifies

The server stores the public key with the account and credential ID. It can verify a signature but cannot reverse the public key into the private key or impersonate the authenticator.

The site binding limits scope

The credential is bound to an RP ID. A credential registered for example.com is not offered to examp1e.com, even when the fake page looks identical.

The biometric is not the passkey

Face, fingerprint, or device PIN can locally unlock use of the private key. The biometric template and PIN stay on the device; the server receives only the cryptographic result and verification flags.

    Why passkeys are safer than passwords

    Passkeys remove several properties attackers rely on: a reusable shared secret, a secret that can be typed into the wrong origin, and a server verifier that can be cracked into a usable credential.

    Attack or propertyPasswordPasskey
    What server storesSalted password verifier; weak passwords may be guessed offlinePublic key; cannot create a valid signature
    PhishingUser can type the same secret into an impostor siteCredential is scoped to the real RP ID and origin
    Credential stuffingReused password works across servicesEach credential is unique to one relying party
    ReplaySame password is submitted repeatedlyEvery assertion incorporates a fresh challenge
    Local unlockWebsite normally verifies the passwordDevice verifies PIN/biometric and releases only a signature
    RecoveryEmail, SMS, help desk, or password resetProvider sync/recovery or another registered authenticator
    Attack 1

    Database breach

    Stolen password hashes can enable offline guessing. Stolen public keys do not let the attacker sign, though the breached server may still expose sessions, personal data, recovery controls, or passkey-binding functions.

    Attack 2

    Phishing proxy

    Passwords and manually entered OTPs can be relayed. WebAuthn's domain binding prevents the fake origin from obtaining an assertion for the real RP.

    Attack 3

    Replay

    A recorded assertion contains the previous challenge. The next sign-in uses a different challenge, so replay verification fails.

    What about authenticator apps?

    “Authenticator app” names a container, not one protocol. An app can generate time-based one-time passwords (TOTP), approve push notifications, or even hold passkeys. Compare the method being used.

    Password + TOTP

    Type, switch apps, copy a code

    During setup, scan a QR code containing a shared secret and confirm a generated code. Later, enter your password, open the authenticator, and type the current code—commonly six digits changing every 30 seconds. Save the service’s recovery codes separately.

    Passkey with user verification

    Select an account, unlock, continue

    During setup, approve creation in the system prompt. Later, select a saved credential and unlock its use locally. The browser carries a fresh signature to the correct site; there is no password or OTP to transcribe in this flow.

    Push approval is a third experience

    A push flow asks you to approve a notification; some require matching a number shown on the sign-in screen. Number matching reduces accidental approvals and push fatigue. It does not by itself give a conventional push flow WebAuthn’s origin binding. Check which protocol the app actually uses. Microsoft explains the number-matching experience.

    Does a passkey still need a six-digit code?

    Not inherently. A service can accept a passkey with required local user verification as its complete sign-in, rather than always asking for an additional OTP. A touch that only demonstrates user presence is different from verifying a PIN or biometric; the server must enforce its intended policy. Some services still require extra checks for sensitive actions.

    My default: use passkeys where supported, and use authenticator-based MFA where passkeys are unavailable. Password + TOTP is a meaningful improvement over a password alone, but it is not phishing-resistant. If TOTP remains an alternate sign-in or recovery route, that route still shapes the account’s overall protection.

    Synced and device-bound passkeys

    “The private key never leaves the device” is only correct for device-bound credentials. Synced passkeys copy encrypted key material through a provider so other trusted devices can recover and use it.

    Multi-device

    Synced passkey

    Encrypted credential material is synchronized through a passkey provider such as iCloud Keychain or Google Password Manager. It improves recovery and multi-device use but adds the provider account and recovery process to the security boundary.

    Eligible for NIST AAL2 when properly protected
    Single authenticator

    Device-bound passkey

    The credential is backup-ineligible and stays with one authenticator. Some device-bound credentials are hardware protected, but “device-bound” alone does not prove hardware isolation or AAL3.

    AAL3 additionally requires two factors plus a hardware-protected, isolated, non-exportable key; synced authenticators are not allowed.

    A phone can sign in a computer without copying the key

    In a cross-device flow, the computer displays a QR code and establishes a nearby authenticated channel to the phone. The phone uses its passkey and returns the result; the credential does not have to be installed on the computer.

    What passkeys do not solve

    Passkeys are phishing-resistant authentication, not a force field around the entire account, device, website, or recovery system.

    Device

    Unlocked or compromised endpoint

    A person who can unlock the device may be able to use its passkeys. Malware can manipulate the local session or ask an authenticator to approve an attacker-chosen action.

    Provider

    Sync and recovery compromise

    Synced passkeys depend on encrypted cloud storage, strong provider authentication, and secure recovery. A weak provider recovery path can become the easiest route to the account.

    Website

    Implementation mistakes

    Skipping challenge, origin, RP ID hash, signature, account binding, or user-verification checks can defeat the protocol's guarantees.

    Session

    Cookie theft after sign-in

    WebAuthn protects authentication. A stolen bearer session cookie may still work until it expires or is revoked.

    Fallback

    Weaker recovery and downgrade

    If password, SMS, email, or help-desk recovery remains easier to attack, an adversary can bypass the passkey entirely.

    Privacy

    Attestation and credential metadata

    Attestation can reveal authenticator provenance. Consumer deployments commonly avoid identifying attestation unless policy needs it.

    Operations

    Deletion, loss, and shared devices

    Website records and provider copies can become out of sync. Signing out does not remove a passkey from a shared device's credential manager.

    Compatibility

    Unsupported or restricted environments

    Older platforms, embedded browsers, blocked Bluetooth, and enterprise policy can interrupt creation or cross-device use.

    The useful mental model

    A password asks, “Can you repeat the shared secret?” A passkey asks, “Can your authenticator produce a fresh signature for this exact site?” That removes phishing, reuse, stuffing, and password-verifier cracking from the main sign-in path—but recovery, device security, implementation, and sessions still matter.

    Glossary

    Passkey
    A passwordless FIDO credential: a discoverable WebAuthn credential based on an RP-scoped key pair.
    Public-key cryptography
    Cryptography using a related public and private key pair.
    Private key
    The secret key controlled by the authenticator and used to create signatures.
    Public key
    The non-secret key stored by the website and used to verify signatures.
    Relying party
    The website or application that registers and verifies the credential.
    RP ID
    The domain identifier to which a WebAuthn credential is scoped.
    Origin
    The scheme, host, and port of the calling web page.
    Authenticator
    The hardware or software entity that creates credentials and signs assertions.
    Challenge
    Fresh random bytes issued by the server to bind a response to one short-lived request and prevent replay.
    Assertion
    The signed authentication response returned by WebAuthn.
    Attestation
    Optional evidence about an authenticator's provenance or properties.
    User verification
    A local check such as device PIN, fingerprint, or face recognition, reflected in the UV flag.
    Discoverable credential
    A credential the authenticator can find without the site supplying its credential ID first.
    Signature counter
    An optional authenticator value that can help detect anomalies but is only a risk signal.
