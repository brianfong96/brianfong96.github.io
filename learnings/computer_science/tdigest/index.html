Step 1 of 8  —  The Problem

The Problem: Computing Percentiles on Streams

Modern systems care about percentiles, not averages. API latency, database tail response time, queue depth, and frame render time are usually summarized as p50, p95, p99, or p99.9. The challenge: values arrive continuously, sometimes millions per second.

The exact solution is easy to describe and terrible to scale: store every value, keep them sorted, then index into the array. That gives exact answers, but it costs O(n) memory and requires shuffling a huge amount of data as the stream grows.

That becomes painful when you need percentiles over massive streams, merge summaries across machines, or keep dashboards hot for hours. What we actually want is a tiny summary that answers percentile queries well — especially in the tails.

Why T-Digest matters: in monitoring, p99 is usually more important than p50. A sketch that is mediocre in the middle but sharp at the tails is often exactly what production systems need.

Key Terms

  • Percentile (pN) — the value below which N% of observations fall. p95 = 200ms means 95% of requests finished in ≤ 200ms.
  • Quantile (q) — same concept expressed as a fraction 0→1 instead of 0→100. q=0.95 is p95.
  • Tail — the extreme ends of the distribution (p99, p99.9). This is where rare but painful events live: timeouts, spikes, slowest queries.
  • Sketch / Digest — a compact data structure that summarizes a stream. You can query it for approximate answers without storing every value.
  • δ (delta / compression) — T-Digest's tuning knob. Higher δ = more centroids = more memory but better accuracy. Typical values: 50–300.
  • Centroid — a (mean, count) pair representing a cluster of nearby values. The digest is just a sorted list of centroids.

Real-world example: API latency monitoring

Your API handles 50,000 requests/second. Most respond in 5–50ms, but some hit 2,000ms+. You need to know p99 every 10 seconds for alerting.

  • Exact approach: store 500,000 values per window → ~4MB per metric per 10s window. With 200 endpoints that's 800MB just for one aggregation window.
  • T-Digest (δ=100): ~500 centroids × 12 bytes = 6KB per metric. For 200 endpoints: 1.2MB total. Error at p99 is typically <1%.
  • No upper bound needed: values can range from 0.1ms to 30,000ms. The digest doesn't care about the absolute range — it only tracks relative rank (quantile position).

The Key Insight: Centroids & Compression

A T-Digest does not keep every value. Instead it keeps a short list of centroids. Each centroid stores a mean and a count. Think of it as saying: “these 37 nearby values are well represented by mean = 412.7.”

When a new value arrives, the digest tries to absorb it into the nearest centroid. If that centroid would become too large, the digest creates a new one instead. This is the core compression mechanism.

The trick is asymmetric compression: large centroids in the middle, tiny centroids near p0 and p100. The center can tolerate approximation. The tails cannot.

q (quantile) — a number from 0 to 1 that describes where a centroid sits in the sorted distribution. q = 0 is the absolute minimum, q = 0.5 is the median, q = 1 is the maximum. The algorithm uses q to decide how much compression a centroid is allowed.

limit (maxWeight) — the maximum number of samples a centroid at quantile q is allowed to absorb. Near the tails (q ≈ 0 or q ≈ 1) the limit is very small (often 1–3), preserving extreme-value accuracy. Near the center (q ≈ 0.5) the limit can be hundreds, because median approximation is cheap.

No upper or lower bound on values. The demo clamps to 0–1000 for visual clarity, but real T-Digests accept any floating-point number — negative, zero, millions, whatever arrives. For example, API response latencies might range from 1 ms to 30,000 ms with no fixed cap. T-Digest handles this naturally because it only cares about relative rank (quantile position), not absolute magnitude.

Scale Functions: Why Tails Need More Precision

T-Digest is not “merge whenever values are close.” It uses a scale function that limits how large a centroid can become at a given quantile q. Near q = 0.5 centroids can be large. Near q = 0 or q = 1 they must stay tiny.

A common conceptual description is k(q) = δ / 2π × arcsin(2q - 1). You do not need the exact derivation to use it. The important idea is simple: tails map to tighter capacity limits.

Memory Deep Dive: Compression Factor & Centroids

The main tuning knob is δ (delta), sometimes called the compression factor. Higher δ allows more centroids, which improves accuracy but increases memory.

In practice, a digest often ends up with roughly 3–5 × δ centroids. Each centroid stores a mean and a weight: float64 mean = 8 bytes and int32 count = 4 bytes. That is only 12 bytes per centroid.

A handy rule of thumb is memory ≈ 5δ × 12 bytes. With δ = 100, that is about 6 KB — enough for precise tail latency summaries across huge streams.

Interactive Centroid Visualizer: Step-by-Step Insertion

This is the insertion path for a single value. T-Digest first finds the nearest centroid, checks whether that centroid is allowed to grow, then either merges or creates a new centroid.

If a merge happens, the centroid mean updates to (mean × count + value) / (count + 1). That preserves the weighted average while keeping the summary compact.

Real-World Applications & Summary

Where T-Digest shines

  • Latency monitoring: keep p99 and p99.9 accurate for APIs, queues, and background jobs.
  • Database query planning: approximate row and value distributions for optimizers.
  • Network monitoring: summarize packet latency, jitter, and error tail distributions.
  • A/B testing: compare percentile shifts, not just mean shifts, across cohorts.

Who uses it

Variants of T-Digest show up in systems like Apache Spark, Elasticsearch, InfluxDB, Datadog, and AWS CloudWatch because percentile queries on streams are a universal systems problem.

T-DIGEST — PSEUDOCODE
class TDigest(delta):
    centroids = []
    totalCount = 0

    function add(x):
        if centroids is empty:
            append centroid(mean=x, count=1)
            totalCount += 1
            return

        sort centroids by mean
        c = nearest centroid to x
        q = cumulative quantile around c
        limit = maxWeight(q, delta, totalCount)

        if c.count + 1 ≤ limit:
            c.mean  = (c.mean × c.count + x) / (c.count + 1)
            c.count = c.count + 1
        else:
            append centroid(mean=x, count=1)

        totalCount += 1
        if centroid count is too large:
            compress by greedily merging adjacent centroids

    function quantile(p):
        walk centroids in order
        find the region containing rank p × totalCount
        interpolate between neighboring centroid means
