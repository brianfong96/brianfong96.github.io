Step 1 of 8  —  The Problem

The Problem — Why Data Cubes?

Imagine you run a web API. Every request generates a log line: timestamp, endpoint, region, status_code, latency_ms, user_id. You get 10 million of these per day.

Now your team asks: "What was the p95 latency for /api/orders in us-east last Tuesday?" To answer exactly, you scan all 10M rows, filter to that endpoint + region + day, sort the latencies, and pick the 95th percentile. That takes seconds and touches millions of rows for a single number.

They ask 50 more questions like this every minute — different endpoints, regions, time windows. Each question is a combination of dimensions (time, endpoint, region) with a measure (count, p95, distinct users). Scanning raw data for every question doesn't scale.

The insight: what if we pre-computed the answers? Group all data by every useful combination of dimensions ahead of time, store the aggregated results, and just look them up when asked.

That's a data cube — a structured set of pre-aggregated summaries organized by dimension combinations so that queries become lookups instead of scans.

Why "cube"? Think of a spreadsheet pivot table. With 2 dimensions you get a 2D table. With 3 dimensions you get a 3D cube. With N dimensions it's an N-dimensional hypercube. Each "cell" holds the pre-computed aggregate for that specific combination of dimension values.

Why aggregation matters:

  • COUNT — "how many requests hit /api/orders in us-east?" Just look up the cell → instant.
  • SUM / AVG — "total revenue by product × region?" Pre-summed per cell.
  • DISTINCT COUNT (dcount) — "how many unique users?" This is hard to pre-aggregate exactly (you can't just add dcounts). HyperLogLog solves this — its sketches are mergeable.
  • PERCENTILES (p95, p99) — "what's the tail latency?" Also not additive. T-Digest solves this — its centroids are mergeable.

Simple aggregates (count, sum) are trivially pre-computable. Complex ones (dcount, percentiles) need probabilistic sketches — that's where HLL and T-Digest make data cubes practical.

Key Terms

  • Dimension — a categorical axis you group by (time, endpoint, region, device). These are your "GROUP BY" columns.
  • Measure — a numeric value you aggregate (latency_ms, revenue, request_count). These are your "SUM(x)" or "COUNT(*)" values.
  • Cell — one specific combination of dimension values → its pre-computed measure. E.g., (Monday, /api/orders, us-east) → count=4521, p95=230ms.
  • Cuboid — a "face" of the cube. The full cube has all dimensions. A cuboid drops one or more dimensions (like a sub-GROUP BY). E.g., just (endpoint × region) without time.
  • Lattice — the family of all possible cuboids forms a lattice from the full cube (most detail) down to the apex (one grand total).
  • Materialization — actually computing and storing a cuboid's cells. "Full materialization" = store everything. "Partial" = store only popular cuboids.
Key mental model: a data cube is not just a 3D box. It is the family of aggregations across every useful dimension combination — a lattice of cuboids. Each cell holds pre-computed answers so queries are lookups, not scans.

What is a Data Cube?

Start with raw data. Imagine 1000 API request logs:

timestampendpointregionlatency_msuser_id

... 996 more rows ...

Now build the cube. Choose dimensions: endpoint × region. Choose measures: count, p95(latency). Group the raw rows by every (endpoint, region) combination:

endpointregioncountp95 latency
/api/ordersus-east312230ms
/api/ordersus-west187195ms
/api/orderseu-west98310ms
/api/searchus-east20145ms
/api/searcheu-west14252ms
... (5 endpoints × 4 regions = 20 cells) ...

That table IS a data cube face (a "cuboid"). Each row is a cell. You went from 1000 raw rows → 20 pre-computed cells. Now any query for "p95 latency of /api/orders in us-east" is a direct lookup: 230ms. No scanning.

Add a third dimension (hour) and it becomes a 3D cube: endpoint × region × hour. Now you have 20 cells × 24 hours = 480 cells. Add a 4th dimension (status_code with 5 values) → 2,400 cells. This is the exponential growth problem.

Why this matters for aggregation:

  • COUNT / SUM — trivially additive. To roll up from (endpoint × region × hour) to (endpoint × region), just SUM the counts across hours.
  • DISTINCT COUNT — NOT additive! If user_17 appears in both hour 14 and hour 15, you can't just add dcounts. You need HLL sketches that can be merged.
  • PERCENTILES — NOT additive! p95 of group A ≠ p95 of (A ∪ B). You need T-Digest sketches that can be merged across cells.

This is exactly why HLL and T-Digest are so important for data cubes — they make non-additive measures mergeable, so you can roll-up and drill-down without going back to raw data.

How HyperLogLog Fits In

Distinct user counting is a classic cube pain point. Exact COUNT(DISTINCT user_id) per cell means carrying sets or repeatedly rescanning detail rows. HyperLogLog stores a tiny sketch instead.

The reason HLL belongs inside cubes is that sketches are additive by merge: to roll up a dimension, keep the register-wise maximum across child cells. That makes parent cuboids cheap to build.

For the full algorithm, see our HyperLogLog tutorial.

How T-Digest Fits In

Percentiles such as p95 latency are another non-additive measure. Averages compose, but percentiles do not. To roll up cube cells, you need a sketch that preserves distribution shape.

T-Digest compresses samples into centroids. Parent cells merge child centroids and recompress, giving high percentile estimates with far less memory than storing every raw value.

For the full algorithm, see our T-Digest tutorial.

Building a Data Cube — Algorithm Walkthrough

Building a cube is a routing problem: enumerate the cuboids you care about, project each row onto those dimension combinations, update measure state, then derive parent cuboids by merging children.

In practice you rarely materialize every cuboid. Partial materialization keeps the hot faces and computes the rest on demand.

Kusto (Azure Data Explorer) Application

Kusto exposes cube-like behavior through summarize, bin(), materialized views, and sketch types like hll() and tdigest(). You may not manage an explicit OLAP cube object, but the query patterns are the same.

Think in cuboids: every summarize ... by dim1, dim2, dim3 query asks for one cube face. Materialized views are precomputed faces. HLL and T-Digest let those faces stay compact.

GETTING STARTED
1. Create a free cluster. In the Azure portal, create an Azure Data Explorer cluster or use the community / free offering if available in your region.
2. Create a database and table. Define columns like timestamp:datetime, region:string, endpoint:string, latency:real, user_id:string.
3. Ingest sample data. Use the web UI, Kusto Explorer, or an ingestion command to load request logs.
4. Start with summarize. Run grouped queries, then add dcount(), percentile(), hll(), and tdigest() when exactness is too expensive.
5. Add materialized views. Promote the dashboard faces you query constantly into precomputed views.
