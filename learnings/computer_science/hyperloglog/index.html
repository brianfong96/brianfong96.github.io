The Problem: Counting Distinct Elements

Imagine you run a website and you want to answer a simple question: how many unique visitors came today? You might have 50 million log events. How do you count distinct user IDs efficiently?

The naive solution is a hash set — store every unique ID you see. It's exact, but memory grows linearly with distinct elements. 50 million unique users × 8 bytes = 400 MB minimum. Across thousands of daily queries on petabyte-scale data, this is unworkable.

This is the cardinality estimation problem. Cardinality = number of distinct elements in a multiset. The key insight: we don't always need exact counts. An answer of "~48.3 million" is just as useful as "48,312,994" for most analytics — and far cheaper to compute.

Key trade-off: HyperLogLog uses a fixed amount of memory regardless of how many items you add. 10 million or 10 billion — the memory stays the same.

The Key Insight: Leading Zeros & Probability

Flip a fair coin until you get heads. The probability of getting exactly k tails before the first head is 1 / 2k+1. Seeing 5 tails in a row has probability 1/64 — rare.

Now apply this to hash values. A good hash function produces bits that are independently and uniformly 0 or 1. The leading zeros in a hash behave exactly like coin-flip tails. A hash starting with k zeros has probability 1/2k.

Therefore: if the maximum leading-zero count across all hashes is k, you've probably processed around 2k distinct elements. This single bit-pattern observation is the seed of the entire algorithm.

Core intuition: If the rarest bit pattern you've ever seen has k leading zeros, you've probably processed ~2k distinct items to find it.

LogLog: The Predecessor

The Flajolet-Martin (1985) algorithm used a single maximum leading-zero counter, but variance was high (~78%). Durand & Flajolet's LogLog (2003) fixed this by splitting the stream into m sub-streams and averaging.

The idea: use the first b bits of each hash to assign the element to one of m = 2b buckets. Track the max leading zeros in each bucket independently, then take the average. Using m buckets reduces standard error from ~78% to ~1.30 / √m.

The name "LogLog" comes from the memory footprint: with n distinct elements, you need at most log2(log2(n)) bits per register to store the max leading-zero count. At n = 1 billion, that's only 30 bits max per register — fits in 5 bits easily.

Weakness: LogLog uses an arithmetic mean of register values, which is sensitive to outliers. One bucket with an unusually high ρ can skew the whole estimate. HyperLogLog replaces this with a harmonic mean.
LOGLOG — PSEUDOCODE
// Initialize
b = 10                          // bits for bucket index
m = 2^b = 1024                  // number of buckets (registers)
M[0..m-1] = 0                   // all registers start at zero

// ADD element x
function ADD(x):
    h  = hash(x)              // uniform hash (e.g. 64-bit)
    j  = h[0..b-1]             // top b bits → bucket index j ∈ [0, m)
    w  = h[b..]               // remaining bits
    ρ  = leading_zeros(w) + 1  // position of first 1-bit (min=1)
    M[j] = MAX(M[j], ρ)       // keep maximum per bucket

// ESTIMATE cardinality (LogLog estimator)
function COUNT():
    avg = (1/m) × Σ M[j]       // arithmetic mean of all registers
    E   = α_m × m × 2^avg     // α_m ≈ 0.39701 corrects bias
    return E

HyperLogLog: The Full Algorithm

Flajolet, Fusy, Gandouet & Meunier (2007) made one key change: replace the arithmetic mean with a harmonic mean over 2-M[j]. The harmonic mean naturally weights outliers downward. One rogue register with a huge value contributes nearly zero to the sum, making the estimate robust.

This brings the standard error from LogLog's 1.30 / √m down to 1.04 / √m. Two range corrections handle edge cases: linear counting when many registers are still zero (sparse data), and a large-range correction when the estimate is very large relative to the hash space.

HYPERLOGLOG — PSEUDOCODE
// ── Initialize ──────────────────────────────────────────────
b = 10                          // precision bits (typical range: 4–16)
m = 2^b                         // number of registers
M[0..m-1] = 0                   // all registers start at zero

// ── ADD element x ───────────────────────────────────────────
function ADD(x):
    h    = uniform_hash(x)     // 64-bit uniformly distributed hash
    j    = h[0..b-1]            // top b bits → register index j
    w    = h[b..]               // remaining (64-b) bits
    ρ    = leading_zeros(w) + 1 // position of first 1-bit (min=1, max=65-b)
    M[j] = MAX(M[j], ρ)        // update register with maximum

// ── ESTIMATE cardinality ─────────────────────────────────────
function COUNT():
    Z = 1 / Σ( 2^(-M[j]) )       // harmonic mean denominator (sum of 2^-reg)
    E = α_m × m² × Z            // raw HLL estimate

    // ── Small-range correction (linear counting) ─────────────
    if E ≤ 2.5m:
        V = #{j : M[j] == 0}    // count empty registers
        if V > 0:
            E = m × ln(m / V)   // more accurate when data is sparse

    // ── Large-range correction ────────────────────────────────
    if E > (1/30) × 2^32:
        E = -2^32 × ln(1 - E/2^32) // adjust for hash space saturation

    return round(E)

// ── α_m bias correction constants ───────────────────────────
α_16  = 0.673
α_32  = 0.697
α_64  = 0.709
α_m   = 0.7213 / (1 + 1.079/m)  // general formula for m ≥ 128

Memory Deep Dive: How Many Bytes?

The claim "O(log log n) memory" sounds abstract. Let's make it concrete.

What is Precision b?

The precision parameter b is the single "tuning knob" in HyperLogLog. It determines how many of the hash's leading bits are used to select a bucket (register). Specifically:

  • b bits are taken from the front of each hash → they index into one of m = 2b registers.
  • The remaining (64 − b) suffix bits are where we count leading zeros (ρ).
  • Higher b = more registers = better accuracy but more memory.
  • Lower b = fewer registers = less memory but higher variance in the estimate.

Think of it as splitting your data into 2b independent experiments. More experiments → more reliable average → tighter estimate. The standard error is approximately 1.04 / √m, so doubling b's exponent halves the error.

Redis uses b=14 by default. Most production systems use b=12–16 depending on accuracy requirements.

With precision b, there are m = 2b registers. Each register stores a value from 1 to (64 − b + 1) — the maximum possible position of the first 1-bit in the suffix. For b = 10, that's at most 55. To store a number 1–55 you need ⌈log2(55)⌉ = 6 bits per register.

For virtually all practical precision values (b ≤ 58), this works out to exactly 6 bits per register. So the total storage is simply m × 6 bits = 2b × 6 bits = 2b × ¾ bytes. At b = 12 (4,096 registers): 4096 × 6 = 24,576 bits = 3,072 bytes ≈ 3 KB — regardless of whether you've counted 1 item or 1 trillion.

REGISTERS & BITS EXPLAINED

What is a Register?

A register is a tiny counter — one per bucket. It stores a single number: the maximum ρ (position of the first 1-bit in the suffix) seen for any element hashed to that bucket. That's it. Not the elements themselves, not a count of elements — just one small integer per bucket.

If you have b=4 (16 buckets), your entire data structure is just 16 numbers. Each number starts at 0 and only ever increases.

What are "Bits per Register"?

Each register stores the max ρ value. With a 32-bit hash and b=4, the suffix is 28 bits long, so ρ can range from 1 to 29. To store a number up to 29 in binary, you need ⌈log2(29)⌉ = 5 bits.

In practice with 64-bit hashes, registers need 6 bits each. That means each register is less than a single byte — you can pack multiple registers into adjacent bytes with bit manipulation.

Analogy: Imagine 16 sticky notes on a wall, one per bucket. Each note only says a number like "3" or "7". You never write the actual items — just the biggest leading-zeros count seen. That's the entire data structure.

Why It Matters

Redis has built-in PFADD / PFCOUNT commands for HyperLogLog. Each HLL in Redis uses exactly 12 KB (b=14, sparse-optimized). You can count billions of distinct items with a single Redis key.

Google BigQuery, Apache Spark, and Apache Flink all use HLL for COUNT DISTINCT on massive datasets. Without it, a single GROUP BY query could require shuffling gigabytes of data across a cluster just to deduplicate IDs.

HyperLogLog++ (2013, Google) refined the original with empirical bias-correction tables and a sparse register format for small cardinalities. It's now the de facto standard. The core idea — hash to bits, count leading zeros, track the max — remains unchanged from Flajolet's 2007 insight.

The key trade-off is elegant: give up exact counts (typically <2% error) in exchange for constant memory. Knowing you had about 48.3 million unique visitors is just as actionable as knowing you had exactly 48,312,994 — and orders of magnitude cheaper to compute at scale.

Summary: Hash every element. Split the hash into a register index (top b bits) and a suffix. Track the max leading-zero position (ρ) per register. Estimate cardinality with α_m × m² × harmonic_mean(2-M[j]). That's it.
